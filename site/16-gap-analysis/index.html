    16. Architecture & Security Critique: Gap Analysis

    A review of this guide's architecture, installer engine, and security model, benchmarked against production plugin ecosystems (vTiger, Frappe/ERPNext).

    16.1 What's Actually Solid

    • Declarative-only modules (no arbitrary backend code shipped in a module) is the right call for a multi-tenant SaaS. It's the same philosophy Frappe uses with its "app" fixtures/hooks system, just pushed further toward pure JSON.
    • SQL identifier whitelisting (^[a-z0-9_]{1,63}$) enforced before any DDL string interpolation is correct, and it's a check a lot of homegrown systems skip.
    • Two-phase FK resolution (create relation columns as plain UUIDs first, apply FK constraints after all modules are loaded) solves a real, non-obvious ordering problem — most amateur module systems get this wrong or ignore it.
    • Transactional install with concurrency locking and rollback is table stakes for a multi-tenant installer, but at least it's actually implemented here, not just described.
    • RBAC + ABAC split (role_model_access, role_field_access, role_record_rule) roughly mirrors what vTiger calls "sharing rules" and field-level security — a reasonable shape for a permissions model.

    16.2 Where It Falls Short of a Real Plugin System

    1. No provenance or integrity verification of a module before install: No checksum, signature, or publisher identity attached to a module package.
    2. No permission/consent surface for admins: No OAuth-style scope list shown to the installing admin before clicking Install.
    3. postMessage("*") origin vulnerability: Using "*" target origin in reference widgets defeats iframe sandboxing. Must validate event.origin.
    4. "Isolated process sandbox" for hooks is underspecified: Timeout and memory limits are described, but the container primitive (gVisor, Firecracker, nsjail, Docker) is unstated.
    5. Audit logging is an afterthought: _record_audit_log fires only on install failure. No runtime audit trail for queries or integration calls.
    6. No per-tenant resource quotas: No limits on max tables per module, storage caps, or execution rate limits.
    7. domain_filter.operator missing explicit whitelist: Needs explicit regex/enum validation before SQL interpolation.
    8. No secrets/credentials story: No encrypted config or vault mechanism for external API keys.
    9. No uninstall data-retention policy: Soft-delete applies to CRUD, but uninstall table retention policy is undefined.
    10. No compatibility gate between module and host platform version: Missing requires_platform_version SemVer guard rail.

    16.3 Priority Order to Close the Gaps

    Priority Gap Why it's urgent
    1 postMessage("*") origin bug Actively vulnerable pattern already in reference docs
    2 domain_filter.operator whitelist Potential SQL injection path, inconsistent with rest of spec's rigor
    3 Module provenance/signing Foundational — everything else assumes you trust the module folder
    4 Named sandbox mechanism for hooks Current isolation claims aren't verifiable without this
    5 Runtime audit trail (not just install-failure logging) Needed for incident response and compliance
    6 Per-tenant resource quotas Prevents a single module from degrading the whole platform
    7 Install-time permission/consent screen Admin trust and transparency
    8 Secrets management channel Currently no sanctioned way for a module to hold a credential
    9 Uninstall data-retention policy Operational gap, will surface in production incidents
    10 Platform/module version compatibility gate Prevents silent breakage on platform upgrades

    17. Installer Engine: Internal Bugs & Lifecycle Completeness Gaps

    • Foreign key failures are silently swallowed: Failed FK constraints log warnings instead of stopping install.
    • Exposed-function schema checks only verify key presence, not type: Schema validator checks key exists, not that type matches.
    • Exposed function implementations run unsandboxed, in-process: Functions execute directly in host process without memory/timeout limits.
    • Successful installs are never audit-logged: Only failure branch writes to audit log.
    • Cache invalidation happens outside error handling: Occurs outside try/finally block after lock release.
    • Missing lifecycle operations: No fully specified uninstall sequence or upgrade migration caller. No installer idempotency check.
    • Installed-module state table schema is missing: Storage schema for sys_installed_module is unstated.

    18. Missing Engine: Runtime Access Enforcement (chokepoint.py)

    • security/access.json declares rules; it does not enforce them.
    • Every call to /api/data/* requires runtime enforcement:
    • Resolve calling user role for account.
    • Check role_model_access for CRUD permission.
    • Check role_field_access to build column allow-lists for read/write.
    • Check role_record_rule to append domain_filter SQL conditions alongside account_id.
    • Execute query safely.

    19. Missing Link: Role Ownership vs Platform User Management

    Recommended Fix: Modules Declare Permission Points, Never Roles

    1. Modules declare models, fields, and features: security/access.json becomes a permission catalog file listing available capabilities.
    2. Engine 4 registers permission points into platform catalog: Platform role system creates roles and assigns users to them.
    3. Resolves authority conflicts, assignment APIs, and role-name collisions.
